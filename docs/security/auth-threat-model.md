# Sign-in threat model

What can go wrong with signing in, what stops it, and the test that proves it. A row with no test says **MISSING**, and the gap is listed at the end.

**Covered:** sign-up, sign-in, access and refresh tokens, refresh, email verification, password reset, roles, ownership, two-step sign-in, lockout, origin checks, sessions and the demo logins. The design is in [ADR 0011](../adr/0011-first-party-authentication.md); what each field holds and how long it is kept is in the [data inventory](../privacy/data-inventory.md).

**How to read the table:** paths are from the repo root. A test is written as `file` › "test name". `auth.e2e` is `apps/api/test/auth.e2e-spec.ts`; other `*.spec.ts` files sit next to the code in `apps/api/src`.

## Trust boundaries

| Boundary                                        | What crosses it                                                                                                  | Trusted?                                                                                      |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| Browser → API                                   | Passwords, codes, the access token (header), the refresh cookie, `Origin`, the user agent                        | No. Everything is checked by the API.                                                         |
| API → Postgres                                  | Users, argon2id hashes, SHA-256 hashes of refresh, email and recovery tokens, the sealed TOTP secret, audit rows | Yes, over a private connection. A leak of the database must not hand out working credentials. |
| API → Valkey                                    | Rate-limit counters and lockout counters, keyed by IP, by a SHA-256 of the email or by a SHA-256 of the user id  | Yes. If Valkey is down, both fail open (see Accepted risks).                                  |
| API → mail (Mailpit locally, off in production) | Verification and reset links                                                                                     | The mailbox is the user's. A link proves only that someone read that mailbox.                 |

## STRIDE

### Spoofing

| Threat                                 | What stops it                                                                                                              | Where in the code                                                                                                                                       | Test that proves it                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Guessed password                       | argon2id; 5 wrong tries lock the email for 15 minutes; two-step when on                                                    | `apps/api/src/auth/auth.service.ts` `AuthService.signIn`; `apps/api/src/auth/lockout.service.ts` `LockoutService`                                       | `auth.e2e` › "locks an email after 5 wrong passwords: the sixth try answers 429, even a right one"; `auth.service.spec.ts` › "answers 429 for a locked email before checking the password, even a right one"; `auth.e2e` › "asks for the code after the password, and lets each code in only once"                                               |
| Guessing at speed from one IP          | 10 requests a minute per IP on every `/auth` and `/auth/2fa` route                                                         | `apps/api/src/auth/auth.controller.ts` and `two-step.controller.ts` `@Throttle` with `AUTH_RATE_LIMIT` (`apps/api/src/rate-limit/rate-limit.module.ts`) | **MISSING** (only the global 100-a-minute limit is tested: `apps/api/test/rate-limit.e2e-spec.ts` › "answers the first 100 requests and rejects the 101st with 429")                                                                                                                                                                             |
| Stolen access token                    | Lives 15 minutes; held in memory by the page, never in storage; names its session (`sid`)                                  | `apps/api/src/auth/tokens.service.ts` `ACCESS_TOKEN_SECONDS`, `TokensService.signAccess`                                                                | `tokens.service.spec.ts` › "rejects an access token after 15 minutes"; `auth.guard.spec.ts` › "refuses an expired token"                                                                                                                                                                                                                         |
| Stolen refresh cookie                  | httpOnly; `SameSite=None; Secure` in production; one use, then rotated; a reused token revokes its whole family            | `apps/api/src/auth/cookie.ts` `refreshCookieOptions`; `AuthService.refresh`; `apps/api/src/auth/revoke-family.ts` `revokeFamily`                        | `cookie.spec.ts` › "is cross-site and HTTPS-only in production"; `auth.e2e` › "signs in with an access token and an httpOnly refresh cookie"; `auth.e2e` › "revokes the whole family when an old token is reused"; `auth.service.spec.ts` › "treats losing a race for the same token as reuse"                                                   |
| Stolen database copy of refresh tokens | Only the SHA-256 hash is stored                                                                                            | `apps/api/src/auth/tokens.service.ts` `hashToken`                                                                                                       | `tokens.service.spec.ts` › "makes a 32-byte refresh token whose stored form is its SHA-256 hash"; `auth.service.spec.ts` › "answers an access token and stores only the refresh token's hash"                                                                                                                                                    |
| Stolen email link (verify or reset)    | Only the hash is stored; single use, even when two clicks race; expires; a reset uses up every older reset link            | `AuthService.verifyEmail`, `AuthService.resetPassword`, `AuthService.sendVerification`, `AuthService.sendReset`                                         | `auth.service.spec.ts` › "with mail on, creates an unconfirmed customer and mails a link stored only as its hash"; `auth.service.spec.ts` › "refuses the loser of two clicks racing with the same link"; `auth.e2e` › "gives a used, an expired and a made-up link the same 400"; `auth.e2e` › "uses up every older reset link when one is used" |
| Forged or expired two-step challenge   | HS256 signature, 5-minute life, `purpose` claim required                                                                   | `TokensService.signChallenge`, `TokensService.verifyChallenge`                                                                                          | `auth.service.spec.ts` › "answers 401 for an expired, forged or wrong-purpose challenge, and checks no code"; `auth.e2e` › "refuses an expired challenge"; `tokens.service.spec.ts` › "rejects a challenge without a user"                                                                                                                       |
| Replayed authenticator code            | The accepted time step is stored; that code and older ones are refused; one conditional update, so a race lets one through | `apps/api/src/auth/two-step.service.ts` `TwoStepService.accept` (`totpLastStep`)                                                                        | `two-step.service.spec.ts` › "refuses the same app code a second time"; `two-step.service.spec.ts` › "lets only one of two sign-ins racing with the same code through"                                                                                                                                                                           |
| Reused recovery code                   | Stored as a hash, marked used in one conditional update                                                                    | `TwoStepService.accept`; `apps/api/src/auth/recovery-codes.ts` `hashRecoveryCode`                                                                       | `two-step.service.spec.ts` › "takes an unused recovery code once, marks it used, and audits both"; `auth.e2e` › "asks for the code after the password, and lets each code in only once"                                                                                                                                                          |
| Guessing the second step               | 5 wrong codes lock the account's second step for 15 minutes (keyed by user id)                                             | `AuthService.verifyTwoStep`; `lockout.service.ts` `userLockKey`                                                                                         | `auth.e2e` › "locks the second step after 5 wrong codes, even for a right code"; `auth.service.spec.ts` › "answers 429 once the account's codes are locked, without checking the code"                                                                                                                                                           |
| Sign-in to an unconfirmed account      | With mail on, sign-in refuses until the link is used (with the right password only)                                        | `AuthService.signIn` (`EMAIL_NOT_CONFIRMED`)                                                                                                            | `auth.e2e` › "mails a link, refuses sign-in until it is used, then lets the account in"                                                                                                                                                                                                                                                          |

### Tampering

| Threat                                            | What stops it                                                                                               | Where in the code                                                                                                                 | Test that proves it                                                                                                                                                                                                                               |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Edited access token (role, subject)               | HS256 signature checked with `JWT_SECRET`; production won't start without the secret; sub and role required | `TokensService.verifyAccess`; `apps/api/src/auth/auth.guard.ts` `AuthGuard`; `apps/api/src/auth/jwt-secret.ts` `requireJwtSecret` | `auth.guard.spec.ts` › "refuses a token signed with another key"; `auth.guard.spec.ts` › "refuses a token without a role or without a subject"; `jwt-secret.spec.ts` › "stops production from starting without JWT_SECRET"                        |
| Token with another algorithm (`alg: none`, RS256) | `verifyAccess` accepts only `algorithms: ["HS256"]`                                                         | `TokensService.verifyAccess`                                                                                                      | **MISSING** (no test sends an unsigned or differently signed-algorithm token)                                                                                                                                                                     |
| Access token used as a challenge, or the reverse  | Challenges carry `purpose`; `verifyAccess` refuses any token with a purpose, `verifyChallenge` requires it  | `TokensService.verifyAccess`, `TokensService.verifyChallenge`                                                                     | `tokens.service.spec.ts` › "never takes a challenge as an access token"; `tokens.service.spec.ts` › "never takes an access token as a challenge"; `auth.e2e` › "never takes a challenge as an access token, or an access token as a challenge"    |
| Cross-site request to refresh or sign-out (CSRF)  | `OriginGuard`: a request with the cookie must come from `WEB_ORIGINS`; no Origin plus a cookie is refused   | `apps/api/src/auth/origin.guard.ts` `OriginGuard`; `apps/api/src/auth/web-origins.ts` `webOrigins`                                | `origin.guard.spec.ts` › "refuses another site with 403, cookie or not"; `origin.guard.spec.ts` › "refuses a request with the cookie but no Origin"; `auth.e2e` › "refuses the cookie routes from another site, or with the cookie and no Origin" |
| Another site reading API answers                  | CORS allows only `WEB_ORIGINS`, with credentials                                                            | `apps/api/src/main.ts` `app.enableCors`                                                                                           | **MISSING** (no test checks the `Access-Control-Allow-Origin` answer)                                                                                                                                                                             |
| Edited TOTP secret in the database                | AES-256-GCM: a changed text or another key fails the tag check instead of giving a wrong secret             | `apps/api/src/auth/secret-box.ts` `seal`, `open`                                                                                  | `secret-box.spec.ts` › "fails on another key or a changed text instead of giving a wrong secret"                                                                                                                                                  |
| Sign-up that sets its own role or flags           | The sign-up schema is strict; the server sets `role` to `NEW_ACCOUNT_ROLE`                                  | `packages/types/src/auth.ts` `signUpInputSchema`; `AuthService.signUp`                                                            | `packages/types/src/auth.test.ts` › "fails on an unknown field such as role"; `auth.e2e` › "creates a visitor customer and stores only an argon2id hash"                                                                                          |

### Repudiation

| Threat                                     | What stops it                                                                                                                                                                      | Where in the code                                                                                                        | Test that proves it                                                                                                                                                                                                                                                                                                                     |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| "I never signed in" / "I never changed it" | Audit rows for sign-up, sign-in, failed sign-in, lockout, every two-step step, refresh reuse, sign-out, email verify, password reset and ending a session; each has the request id | `apps/api/src/audit/audit.service.ts` `AuditService.record`; calls in `AuthService`, `TwoStepService`, `SessionsService` | `auth.service.spec.ts` › "records the sign-in and clears the email's failures, with no email in the record"; `two-step.service.spec.ts` › "takes a right app code, stores its time step, and audits the sign-in"; `sessions.service.spec.ts` (`apps/api/src/users`) › "revokes the whole family and audits it with no email or browser" |
| Failed sign-ins with no account to tie to  | Recorded with no actor and no target, and never the email                                                                                                                          | `AuthService.failed`; `AuditService.record`                                                                              | `auth.service.spec.ts` › "counts an unknown email the same way, recorded with no actor, no target and no email"; `audit.service.spec.ts` › "writes an event about no known account with no actor and no target"                                                                                                                         |
| Audit rows leaking secrets                 | No email, password, code or token in an audit row                                                                                                                                  | `AuditService.record` callers                                                                                            | `auth.service.spec.ts` › "records the sign-in and clears the email's failures, with no email in the record"                                                                                                                                                                                                                             |

**Not audited, stated plainly:** successful refreshes; refresh failures other than reuse; used, expired or made-up email links; wrong codes on two-step **enable** and **disable** (only wrong codes at sign-in are recorded, as `auth.2fa.failed`); `GET /me`; listing sessions; requests refused by `OriginGuard`, the rate limit or CORS.

| Password hashes leak                               | argon2id at 19 MiB, 2 passes, 1 lane, random salt                                                                                                                 | `apps/api/src/auth/argon2-options.ts` `ARGON2_OPTIONS`; `apps/api/src/auth/password.service.ts` `PasswordService` | `password.service.spec.ts` › "stores an argon2id hash with the OWASP minimum settings, not the password"; `password.service.spec.ts` › "gives two different hashes for the same password"                                                                                                      |
| Finding out which emails have accounts: sign-in    | Wrong password and unknown email give the same 401; an unknown email still costs one hash check; an unconfirmed account is only revealed after the right password | `AuthService.signIn`, `AuthService.dummyHash` (`SIGN_IN_FAILED`)                                                  | `auth.e2e` › "gives a wrong password and an unknown email the same 401"; `auth.service.spec.ts` › "gives an unknown email the same answer, after checking a dummy hash"; `auth.e2e` › "never says whether the account is confirmed to a wrong password"                                        |
| Same, through sign-up                              | A taken email gets the generic answer and no mail                                                                                                                 | `AuthService.signUp` (`SIGN_UP_FAILED`)                                                                           | `auth.e2e` › "gives the generic answer for a taken email"; `auth.e2e` › "sends no mail for a taken email"                                                                                                                                                                                      |

| Secrets at rest                                    | TOTP secret sealed with AES-256-GCM (`TOTP_KEY`, required in production); refresh, email and recovery tokens stored only as hashes                                | `secret-box.ts` `seal`; `apps/api/src/auth/totp-key.ts` `requireTotpKey`; `hashToken`; `hashRecoveryCode`         | `secret-box.spec.ts` › "round-trips, and the stored text never contains the secret"; `totp-key.spec.ts` › "stops production from starting without a usable key"; `two-step.service.spec.ts` › "switches on with a right code and answers 10 recovery codes, stored only as hashes"             |
| Secrets in logs                                    | Pino redacts `authorization`, `cookie`, `set-cookie`, and any `password`, `token` or `email` field; a failed mail is logged without address or token              | `apps/api/src/logging/logging.config.ts` `REDACT_PATHS`; `AuthService.sendReset`                                  | `apps/api/src/logging/logging.spec.ts` › "keeps an email and a password out of the log output"; `logging.spec.ts` › "blanks the authorization and cookie headers"; `auth.service.spec.ts` › "logs a failed send without the address or the token"                                              |

### Denial of service

| Threat                              | What stops it                                                                                                               | Where in the code                                                                                | Test that proves it                                                                                                                                                                                                                                      |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Flood of guesses                    | Rate limit (100 a minute per IP everywhere, 10 on auth routes) plus the per-email and per-account lockout                   | `rate-limit.module.ts` `RateLimitModule`; `@Throttle` on the auth controllers; `LockoutService`  | `rate-limit.e2e-spec.ts` › "answers the first 100 requests and rejects the 101st with 429"; `auth.e2e` › "locks an email after 5 wrong passwords: the sixth try answers 429, even a right one"; the 10-a-minute auth limit is **MISSING** (see Spoofing) |
| Hash cost used to tie up the server | argon2id costs about 19 MiB per check; sign-in is throttled at 10 a minute per IP; a locked email is refused before hashing | `ARGON2_OPTIONS`; `AuthService.signIn` (`assertOpen` before `verify`)                            | `auth.service.spec.ts` › "answers 429 for a locked email before checking the password, even a right one"; the throttle part is **MISSING**                                                                                                               |
| Locking a known user out            | Not stopped: anyone who knows an email can lock it for 15 minutes. Accepted (see below)                                     | `emailLockKey`                                                                                   | `auth.e2e` › "locks an email after 5 wrong passwords: the sixth try answers 429, even a right one" (proves the behaviour, which is the risk)                                                                                                             |
| Valkey down                         | Rate limit and lockout both fail open, so sign-in keeps working. Accepted (see below)                                       | `apps/api/src/rate-limit/valkey-throttler.storage.ts` `ValkeyThrottlerStorage`; `LockoutService` | `valkey-throttler.storage.spec.ts` › "lets the request through when Valkey is down"; `lockout.service.spec.ts` › "lets everything through when Valkey is down"                                                                                           |
| A lockout answer with no retry hint | 429 carries `Retry-After`                                                                                                   | `ProblemDetailsFilter`; `apps/api/src/errors/too-many-tries.exception.ts`                        | `problem-details.filter.spec.ts` › "sends Retry-After with a lockout's 429"                                                                                                                                                                              |

| Choosing your own role                                      | The role comes only from the server: stored on the user, signed into the token; sign-up always gives `customer` | `AuthService.signUp` (`NEW_ACCOUNT_ROLE`); `TokensService.signAccess` | `auth.service.spec.ts` › "creates a confirmed customer with the hash when mail is off, and sends nothing"; `packages/types/src/auth.test.ts` › "fails on an unknown field such as role" |
| Reaching another user's records                             | `assertOwner` on every owned record; queries filtered by the token's user id                                    | `assertOwner`; `SessionsService.end`                                  | `ownership.e2e-spec.ts` › "shows user B only their own cart and orders"; `ownership.e2e-spec.ts` › "lets a seller rename only their own store, and audits it"                           |

| Seller staff acting for any seller                          | Not built: `seller_staff` has no link to a seller yet (Phase 10), so no route grants it seller powers           | `packages/types/src/roles.ts` `roleSchema`                            | `roles.e2e-spec.ts` › "$method $url as $role answers $expected" (seller routes refuse `seller_staff`)                                                                                   |
| An ended session or a demoted role keeps working            | The access token stays valid until it expires (at most 15 minutes). Accepted in ADR 0011                        | `AuthGuard` (no database lookup)                                      | `auth.e2e` › "lists two sign-ins, flags the current one, and ends one of them" (proves the refresh stops; the 15-minute window is by design)                                            |

## Accepted risks

| Risk                                                                                     | Why it is accepted                                                             | What limits it                                                                                                              |
| ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| Anyone who knows an email can lock it for 15 minutes                                     | Locking per email is what stops slow guessing from many IPs                    | 15 minutes, then it clears; the user can wait or use another session that's already signed in                               |
| Valkey down means no rate limit and no lockout                                           | A demo that can't sign anyone in is worse than a short window without counters | argon2id still makes each guess slow, and the window lasts only as long as the outage                                       |
| An access token outlives sign-out, an ended session or a role change by up to 15 minutes | Checking tokens without a database lookup (ADR 0011)                           | 15-minute life; the refresh token is revoked at once                                                                        |
| The demo logins, including admin and support, are public                                 | They are how people try the demo                                               | All data is made up or visitor-entered, visitors are told to use made-up details, and the nightly reset restores everything |

## What this model does not cover

- Sign-in with Google or another provider: moves to Phase 13, with real email.
- Payments (simulated today, no card data stored).
- The seller console app.
- The hosting platforms' own security (Neon, Render, Vercel) and the GitHub workflows.

## Gaps

| Gap                                                                                                                           | Suggested card                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| No test for the 10-a-minute limit on auth routes                                                                              | Add an e2e test: the 11th sign-in from one IP within a minute answers 429, and the same holds for `/auth/2fa`      |
| No test for a token with another algorithm                                                                                    | Add a tokens test: an unsigned (`alg: none`) token and a token with a different algorithm are refused              |
| No test for the CORS answer                                                                                                   | Add an e2e test: the shop's origin gets `Access-Control-Allow-Origin` and credentials, another origin gets neither |
| Wrong codes on two-step enable and disable are neither counted by the lockout nor audited                                     | Count and audit wrong codes on enable and disable like sign-in codes                                               |
| Anyone can switch on two-step for a public demo login, or lock its email, and shut other visitors out until the nightly reset | Refuse two-step set-up for demo logins, and consider not locking them out (the throttle still applies)             |
